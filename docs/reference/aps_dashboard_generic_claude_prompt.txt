# 6. Dashboard Performance & Google Sheet Read Optimization — Mandatory for Every Change

Performance is a requirement for **every future feature and bug fix**, not a separate optional task.

**Never trade data accuracy, security, data integrity, or existing functionality for performance.** Do not add new APIs, libraries, frameworks, or external services just for performance. Make **small, surgical, measurable changes**; do not rewrite working code.

### 6.1 Before and after — measure

Before changing code, and again after, identify where practical:
- execution time of the affected server functions
- major Google Sheet reads/writes (which sheet/range, how many times per request)
- `google.script.run` server calls per screen/action
- Classroom / Zoho / other API calls
- payload size returned to the browser
- cache usage (hits, misses, invalidation)
- expensive or repeated processing (loops, scans, sorts, JSON parse/stringify)

Report the difference in the final report (§25, item 7). If measurement is not possible, say so.

### 6.2 Google Sheet reads

Pattern:

`one bulk read → validate/normalize → build indexed lookup maps → process in memory → reuse the result`

- Read each sheet/range **at most once per request**. Pass the values (or the built map) to the functions that need them; do not read the same sheet/range again within the same request.
- Do not call `SpreadsheetApp.open*`, `getSheetByName()`, `getDataRange()`, `getRange()`, `getValues()`, or `getValue()` inside loops or inside helper functions that are called repeatedly when the same data can be read once and reused (pass it in, or memoize it for the current execution).
- Read only the needed range when it is known; avoid `getDataRange()` when a known range is sufficient.
- Use indexed lookup maps (by ID, email, APSID, course ID, etc.) for frequently searched datasets instead of repeatedly filtering/scanning large arrays.
- Never read a Sheet again when the current request already has the data.
- Reuse existing Sheet helpers and the data access steps in §7.

### 6.3 Caching

- Use CacheService for appropriate **non-critical, reusable** data (rules in §14).
- Invalidate or version the cache after **every write** that changes the cached data.
- Respect CacheService size limits (about 100 KB per value); chunk or skip caching large values.
- Never cache real-time or critical data without a freshness rule.

### 6.4 Google Classroom / Google APIs

- Never call Classroom APIs merely to render data already stored in the Dashboard Sheet/cache.
- Avoid duplicate course, roster, topic, coursework, Meet, Directory, Reports, Drive, or other API calls.
- Reuse data already loaded during the request.
- Batch/paginate only when required.
- Retry only transient errors with bounded backoff.
- Do not add a new API call if an existing Sheet/cache/helper can provide the required value.

### 6.5 Browser / `google.script.run`

- Minimize server round trips; reuse the existing request batching where it exists.
- Prevent duplicate and overlapping requests; do not trigger the same load from multiple initialization paths.
- Avoid unnecessary polling; pause nonessential polling when the tab is hidden; preserve existing realtime behavior where required.
- Lazy-load expensive tabs/data when this does not change existing behavior.
- Return only the data required by the current UI; do not send full datasets unnecessarily.
- Refresh only the affected UI section; never rebuild the entire Dashboard for one change. Preserve existing data on screen during background refresh and avoid unnecessary loading/flicker (details in §8).

### 6.6 Writes

- Batch Google Sheet writes with `setValues()` where safe; no cell-by-cell writes.
- Use `LockService` for read-modify-write operations.
- Keep writes idempotent.

# 7. Data Access Pattern

Checklist for each request (rules in §6.2–6.3):

1. Determine the minimum data actually required.
2. Read each required source once where practical.
3. Normalize once.
4. Build indexed maps for repeated lookups.
5. Reuse those maps for all subsequent operations.
6. Return only required fields.
7. Cache only data whose freshness rules permit caching.

Do not blindly cache real-time data.

## B2. Migration approach (strangler pattern)

- Move one module at a time. Apps Script stays the live system until each module is proven on Azure.
- Every user-visible behavior must stay identical: same tabs, labels, roles, messages, emails,
  Sheet columns and audit records. "Do NOT change existing features" (Part A) applies to the port.
- Keep the **same function names** as `Code.gs`. The browser still calls `google.script.run.<fn>`;
  `public/aps-gas-shim.js` sends it to `POST /api/run/<fn>`, answered by `src/api/registry.ts`.
- A function not yet ported must return the standard "not on Azure yet" message — never a fake result.
- Helper functions ending in `_` are never callable from the browser.
- Google Sheets remain the system of record until a later phase explicitly approves a database move.

---

## B3. Parity is mandatory

For every ported function:
1. Read the current `Code.gs` implementation (and its `CURRENT_PROD_CODE` version) first.
2. Port the logic with the same inputs, outputs, ordering, rounding, messages and edge cases.
3. Add a parity test that runs the `Code.gs` function in gasmock (`gas-source/`) and the TypeScript
   port on the same data, and compares results.
4. Run `npm test` and `npm run test:gas`. Report results exactly as executed.

Generated or shared tables (for example the Access Control catalog) must be derived from `Code.gs`,
not retyped by hand.

---

## B4. Identity, roles and security on Azure

- Sign-in: Google OAuth code flow, single-use state nonce, ID token verified server-side.
- Allowed domains, role order, APSID rules and Access Control come from the ported Code.gs logic.
- Every protected endpoint starts with `requireSession` / `requireTab` — server-side, always.
- Never trust client role, client email, hidden buttons or browser parameters (Part A §9).
- `DEV_LOGIN` is for local development only and must be refused in Azure and production.
- Session tokens, OAuth codes, ID tokens, access tokens and service-account keys must never appear in
  logs, error messages, the browser, audit records or test output.

---

## B5. Secrets and configuration

- All secrets live in **Azure Key Vault**, read by the App Service **managed identity**
  through Key Vault references. Never in code, `.env` files committed to git, Bicep, or the workflow.
- `.env.example` lists setting names only, never values.
- Google access uses a **service account with domain-wide delegation**, scopes kept to the minimum.
- Deployment uses **GitHub Actions with OIDC** (no long-lived Azure credentials in GitHub).
- An unresolved Key Vault reference counts as "not set"; the app must start safely and explain what is missing.

## B6. Apps Script → Azure mapping

| Apps Script | Azure equivalent |
|---|---|
| `doGet` / HtmlService | Express `GET /` + `src/web/render.ts` (known scriptlets only) |
| `google.script.run` | `aps-gas-shim.js` → `POST /api/run/:fn` (`{ok}` / `{err}`) |
| `SpreadsheetApp` reads | Sheets API `values.batchGet` + TTL cache with in-flight de-duplication |
| `SpreadsheetApp` writes | Sheets API `batchUpdate` / `values.batchUpdate` — one batched call per action |
| `CacheService` | In-process TTL cache now; Azure Cache for Redis only if scale requires it |
| `PropertiesService` | Planned per phase (Key Vault for secrets; table/Sheet storage for data) |
| `LockService` | Planned per phase (single-instance lock now; distributed lock before scale-out) |
| Time triggers | Planned: Azure Functions timer triggers (one scheduler, same schedules) |
| `MailApp` / `GmailApp` | Gmail API via the service account, same templates and branding |
| `ClassroomApp` / Admin APIs | Google REST APIs via the service account, same course filters |
| `Logger` / execution log | Application Insights (no secrets, no tokens, no personal data beyond what is needed) |

Do not choose a new service for a mapped item without stating why and getting approval.

## B7. Performance on Azure (adds to Part A §6)

- Read each Sheet range at most once per request; batch ranges with `batchGet`.
- Cache by the same freshness rules Apps Script uses; never cache realtime data longer than Apps Script did.
- Keep payloads at least as small as the Apps Script version; do not send fields the browser does not use.
- Retry Google API calls only on transient errors, with bounded back-off.
- Measure before/after where practical and report it.

## B8. Infrastructure and deployment

- Infrastructure changes go in `infra/main.bicep` only — no manual portal-only changes without recording them.
- Node.js version must be a **supported LTS** and identical in `package.json` engines, Bicep and the workflow.
- The workflow lives at `.github/workflows/azure-deploy.yml` (copy kept at `docs/azure-deploy.yml.txt`;
  keep both identical).
- `/healthz` must expose no data or secrets.
- Do not deploy, create Azure resources, or change Google Workspace settings unless the user asks.

---

## B9. Testing and reporting on Azure

Required before reporting a change as done:
- `npm test` (TypeScript build + Azure tests, including parity tests)
- `npm run test:gas` when Apps Script reference behavior is involved
- `npm run e2e` when the page, shim or sign-in flow changes

Follow Part A's rule: never claim a test passed unless it was actually run. Anything that needs
Azure, real Google sign-in, real Sheets, or GitHub Actions and was not run must be reported as:
**"Not executed — environment/authorization required."**

The final report (Part A §25) must also state:
- which Code.gs functions were ported or changed, and their parity test results;
- any setting, secret or Azure resource the user must add;
- what still runs only on Apps Script.
